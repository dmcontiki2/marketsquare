Buzz was gated on rules, not on people

MarketSquare · 14 September 2026 · BUZZ-BIND-1 + BUZZ-ACCEPT-1 + IDENTITY-BIND-1 · RUL-135 · enforced in the tree, awaiting the deploy

David asked: “Is the security of the app an issue? Can a none subscriber do things in it which only subscribers should be able? Is the comms gated in that way as well? Even a free trustsquare subscriber is still a subscriber — he read the eula and accepted it and we may already have a TS for him.”

The spreader was never the question. Same origin, same server, same rulebook (RUL-125(a)) — it can be neither safer nor less safe than the app. The answer to the real question was worse: the comms was not gated on identity at all.

The chain, as it stood Four links, each one trusting an email typed into the request body.

Link 1 · the key

The key is public

API_KEY sits in ms.js line 71, served to every browser that loads the site. It is an app string, not a secret — the code's own comment said so a month ago.

Link 2 · the pair

Connect any two people

/buzz/pair takes both addresses from the body and records the connection. Neither of them has to be you.

Link 3 · the switch

Flip the victim's own consent

/buzz/allow believes the email field, so a stranger could switch somebody else's permission on for them. This is the link that matters.

Link 4 · the buzz

Buzz in his name

/buzz sends with from_email's name on it. The 30-an-hour limit was the only brake in the whole chain.

Proved on production, read-only, with an address that does not exist. No real person's data was touched — this is the key deciding an identity-scoped read: 
curl  "…/buzz/pairs?email=nobody@example.invalid"                        → 401
curl -H "X-Api-Key: <the string in ms.js>"  "…/buzz/pairs?email=…"   → 200  []

What was wrong, and what was not

Right, and untouched by this change

  • The pair is the unit of consent, never a global switch.
  • Each side's allow flag belongs to the receiver.
  • Closing is symmetric, told, and only the closer reopens.
  • One line, 120 characters, 30 an hour, 90-day retention.
  • Push first, email backup, never SMS (RUL-122).

Wrong, and it was only ever one thing

  • WHO. Every endpoint let the caller declare his own identity.
  • The rules were then enforced perfectly — against the wrong person.
  • Known class: ACCOUNT-BIND-1 named it on 5 Aug and fixed it for charging.
  • Buzz was built last week and simply never wired to it — my omission.

The gate David named A proven identity plus an acceptance, not a paid one. Nothing in this code asks what anybody pays.

The second half, which the first fix did not cover. Proving WHO does not prove that the who ever agreed to anything. eula_accepted_at is written in exactly one place — the seller flow, at first publish — so somebody who clicked a magic link and never listed had it at NULL, and Buzz would have admitted the precise person §3.8 was written to bind. First switching Buzz on is now the acceptance moment. It asks for no ID: the magic link proves the inbox, the tick makes the terms bind, the ID check opens the trust score — three rungs, and Buzz needs the first two.
Passes

Free member

Email proven by the magic link, §3.8 ticked once. He is a subscriber, and he gets the full comms. One tick, thirty seconds, no document.

Passes

Paying member

Identical treatment. The gate never looks at the plan — that is a different question and it is not asked here.

Refused

Stranger with the public key

No session, no proof of any inbox. 401 on every Buzz endpoint whatever he types in the body, 403 if he signs in and types somebody else's address, and 403 if he signs in and has never ticked.

Where it stands Every stage but one is closed. The one that is left is the double-click, which was always yours.

Why three shapes and not one. A single rule would have got the agency lane wrong: the agent whose row is being changed is the subject, never the actor, so binding to him would have been the wrong fix wearing the right shape. And the admin lane is safe to keep open only because MS_ADMIN_KEY is a different key — env-only, never shipped to a browser — which is what lets the Document Hub keep working for somebody else's documents while the same endpoint called from the app is pinned to the signed-in account.

One cliff, closed rather than left A bound endpoint answering 401 would have shown “API error 401”. The three shared fetch helpers now say, in words, that the sign-in on this device has lapsed. The cookie runs 180 days so this is rare — but rare and silent is the combination that wastes somebody’s evening.
