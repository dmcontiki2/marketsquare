HALT finding 1 — double-charge, raised READ → EXECUTED

accept_intro (PUT /intros/{intro_id}/accept) reads the intro row, then unconditionally writes status='accepted', tuppence_charged=1 and inserts a −1 intro_deduct row. It never tests the flags it is about to set. Replayed against a throwaway SQLite replica — no production data, no production box:

start balance          : 1T
after 1st accept       : 0T   (correct)
after 2nd accept (dbl) : -1T   <-- buyer charged twice for ONE introduction
after 4 total accepts  : -3T   <-- wallet is NEGATIVE, no balance floor
intro_deduct rows      : 4 for 1 introduction
⚠ Operating limit: one accept. Destruct limit: two. A double-click, retry, proxy replay or refresh charges again each time, the wallet has no floor at zero, and the relay and webhook re-fire — both parties get duplicate introduction emails. On a platform whose entire brand is trust and whose only till is Tuppence, this is the defect that loses a founding buyer permanently, and it is invisible to the operator because the intro looks correctly accepted.

HALT finding 2 — NEW: the automatic safe-state response is a placebo

The HALT addendum asks which breaker is real and which is decorative. Here is the honest answer for the BIT Mitigator — the fast, reversible step between “an S1 test is failing at users now” and “a human gets to it”.

Flag it may flipTriggered byIts promiseRead by the app?
auth_fail_closedB-NEG-AUTH (S1, live, passing)force auth closedNO
tuppence_burn_enabledB-NEG-DELIVER-CHARGE“you will not be charged in the meantime”NO
ai_example_enabledB-FEA-EXAMPLE / B-FEA-CONTRACTstop serving AI examplesNO
⚠ A placebo breaker is worse than no breaker. All three flags appear in bea_main.py only at the schema, the migration, the /flags exposure tuple, the write model and the read-back — never at a decision site; neither ms.js nor marketsquare.html reads any of them. The mitigator writes the row, journals the flip and reports the S1 mitigated, while the app carries on unchanged. No breaker at least escalates to a human; a placebo consumes the incident. The worst is tuppence_burn_enabled — the very lever an operator would pull during the double-charge incident above, promising “you will not be charged”, stopping nothing.
ℹ Scope, stated precisely. The detection layer is real — B-NEG-AUTH is a live S1 check and it PASSES today. What is decorative is the automatic mitigation. Two honest fixes, either acceptable: make each flag load-bearing at its decision site, or remove it from SAFE_FLAGS so the mitigator escalates to a human instead of pretending.

Two further defects in the same class

⚠ The EULA promises a mechanism that does not exist. The shipped terms tell a buyer 1T is “committed (held) when the Buyer makes the request” and “released in full if declined or expired”. There is no hold, no release and no balance check at request time anywhere in the code. Fixing the idempotency does not close this — both can be true and this still be false. It is a legal and product exposure, not only an engineering one, and which way it resolves (implement the hold, or change the wording) is David's call. RG-0145.
⚠ Decline is unguarded too. decline_intro writes status='declined' with no transition check, so declining after an accept leaves tuppence_charged=1 with no refund row — the buyer paid for an introduction the record calls declined. Folded into RG-0142 as the same missing-transition-guard class.
⚠ And the assertions themselves were wrong — twice, fixed the same session. The peer found three false-red and three false-green paths in the entries as first written. Worst false-red: RG-0144 read the payload through a helper that transparently retries with the reviewer cookie, so gating the endpoint behind auth — one of the two right answers — would have kept it red forever and pushed a later session to weaken it. Worst false-green appeared on the very next run: RG-0142's own broadened token list let accept_intro's UPDATE ... SET tuppence_charged=1 satisfy the check for code that reads that flag. Guards now match only control flow, never SQL handed to conn.execute. Both corrections are written into the entries' refs — an assertion that is wrong gets fixed and said out loud, never quietly weakened.
