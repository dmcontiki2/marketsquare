# Peer Review Report — AI Auto-Failover P2

## Findings

### [BLOCKER] T2 degradation cannot be implemented from the proposed `ai_breaker` schema

**File:** `AI_AUTO_FAILOVER_P2_DESIGN.md`, §1 and §2

The proposed table stores only:

> `fail_count`, `window_start`, `last_error`, `last_ok_at`

But T2 requires:

> “over a rolling 10 min: ≥ 10 calls AND ≥ 20 % not-ok”

That calculation requires, at minimum, a count of **all calls** and **failed calls** in a time-bounded rolling window. The proposed state cannot distinguish:

- 2 failures out of 10 calls (20%, should trip),
- 2 failures out of 100 calls (2%, should not trip), or
- 2 failures separated by a success.

Further, §3 says:

> “ok -> reset window / close half-open”

Resetting a shared failure window on success makes it impossible to retain the rolling population needed for a ten-minute error-rate calculation.

This is not an implementation detail; the specified state model is insufficient for one of the stated trip rules. Add bounded rolling outcome storage or time buckets keyed by `(provider, task, bucket)` with `attempt_count` and `failure_count`, and define the exact rolling-window aggregation and retention policy.

### [BLOCKER] The proposed half-open behavior silently performs automatic fail-back, contrary to the stated doctrine

**File:** `AI_AUTO_FAILOVER_P2_DESIGN.md`, §0, §3, §5  
**Related file:** `AI_SWAP_ARCHITECTURE.md`, §1, §2, §7

The design repeatedly states:

> “fail-over is automatic, fail-back is manual”

and:

> “There is NO automatic fail-back”

However, §3 specifies:

> “success closes the breaker and fires a ‘ready to restore’ notice”

The proposed chain remains:

```python
chain = [active] + [others]
```

The active provider is not changed when it trips; it is merely excluded by `breaker.allows()`. Therefore, when a half-open call succeeds and the breaker is automatically changed to `closed`, the original active provider is once again first in the chain on the next request. Traffic returns to it automatically.

This is automatic fail-back in practice, regardless of the wording of the dashboard notification.

The state model needs a separate concept such as `ready` / `recovered_pending_restore`, where probes may establish health but the provider remains ineligible for normal routing until an explicit `/admin/ai-restore` action. Alternatively, separate “health state” from “routing state/priority.” A conventional circuit-breaker `closed` state is not compatible with the project’s manual-fail-back policy unless traffic selection is decoupled from breaker state.

### [BLOCKER] Heartbeat probes routed “through the seam” will not reliably probe the failed provider

**File:** `AI_AUTO_FAILOVER_P2_DESIGN.md`, §4  
**Related file:** `ai_provider.py`, `complete()`

§4 says the heartbeat will:

> “send a 10-token ping through the seam for that provider·task”

But current `complete(..., provider=target)` does not mean “call only target.” In `ai_provider.py`:

```python
prov = provider or AI_ACTIVE
...
res = fn(...)
if not res.ok:
    for alt in [p for p in ADAPTERS if p!=prov]:
        ...
        r2=ADAPTERS[alt](...)
        if r2.ok: return r2
```

Thus, a heartbeat aimed at Anthropic that receives an Anthropic failure can successfully return an OpenAI or Scaleway result. Unless the breaker instrumentation is unusually careful, that can:

1. falsely mark the target provider healthy;
2. write the fallback provider’s result against the wrong provider/task row;
3. consume a request on an unrelated standby provider;
4. prevent a real diagnosis of the failed target.

Likewise, a tripped provider is normally filtered out by:

```python
chain = [p for p in chain if breaker.allows(p, task)]
```

A scheduled probe needs an explicit, atomic probe-claim path that bypasses normal routing eligibility for exactly the target provider. It also needs a **direct/no-fallback invocation mode** so the returned outcome is unambiguously attributable to that provider.

The design should define a dedicated internal operation, e.g. `complete(..., provider=target, allow_fallback=False, breaker_probe=True)`, rather than relying on normal user-call semantics.

### [MAJOR] The proposed `AIResult.status` field is insufficient to classify T3, and “one-line change per adapter” understates the work

**File:** `AI_AUTO_FAILOVER_P2_DESIGN.md`, §2  
**Related file:** `ai_provider.py`, `_anthropic`, `_openai`, `_scaleway`

The design says:

> “Adapters must surface the STATUS CLASS for this to work: `AIResult` gains one field, `status` (int HTTP status or None on exception). One-line change per adapter”

But T3 requires more than status:

> “any 401/403, or the provider's explicit ban/credit-exhausted error body”

The current adapters discard the needed information:

- They parse JSON but retain neither the error type/code nor a sanitized error message.
- Any JSON parsing error, including an HTML 5xx response, is caught by the broad `except Exception`, resulting in a generic failed result with no HTTP status.
- Missing credentials return `ok=False`, but no status or configuration classification.
- Exceptions discard the exception class and message.

A reliable implementation needs a structured failure classification, such as:

- `http_status`
- `error_kind` (`timeout`, `connection`, `http_5xx`, `rate_limited`, `unauthorized`, `forbidden`, `credit_exhausted`, `misconfigured`, `invalid_request`, `unknown`)
- sanitized, bounded diagnostic text

This classification must be set even when the response body is malformed. It should also be provider-specific where credit exhaustion is represented by an error code/body rather than a 401/403.

### [MAJOR] Missing or disabled provider credentials would be treated as a service outage and create misleading trips/alerts

**File:** `AI_AUTO_FAILOVER_P2_DESIGN.md`, §2 and §3  
**Related file:** `ai_provider.py`, `_anthropic`, `_openai`, `_scaleway`

The source currently returns `ok=False` when a key is absent:

```python
if not key: return AIResult("",None,None,"openai",model,ok=False)
```

Under the proposed T1 rule, three requests within 120 seconds would trip that provider. This is especially relevant because the P2 document says:

> “OpenAI GPT-5.6 (wired, awaiting key)”

An unprovisioned OpenAI standby is not a provider outage. It is local configuration state and should normally be shown as `disabled`/`unconfigured`, excluded from the routing chain, and not generate a provider-outage alert. The same issue applies to temporarily removed keys during the suggested drill procedure.

The design needs explicit distinction between:

- locally disabled/unconfigured provider;
- provider account/key rejected by a real remote 401/403;
- remote transient outage;
- caller/request error.

Without it, dashboard state, alerting, and incident diagnosis will be inaccurate.

### [MAJOR] SQLite/cache/concurrency behavior is unspecified and can defeat “True-once” half-open semantics

**File:** `AI_AUTO_FAILOVER_P2_DESIGN.md`, §1 and §3

The design proposes:

> “Read through a ~10 s cache exactly like `_ts_active_provider()`”

while also requiring:

> “True-once for `half_open` when `probe_after` has passed”

A ten-second per-process cache and normal SQLite read/update operations do not guarantee “True-once.” Multiple concurrent requests, and especially multiple BEA worker processes, can all observe an eligible half-open row before any writes the probe claim. They can then send multiple probes or live user calls to the provider that is supposed to receive one controlled trial.

This is a correctness and cost issue during recovery and outage flapping. The design needs to specify:

- whether BEA has one process, one worker, or multiple workers;
- the SQLite journal/locking mode;
- an atomic conditional state transition, e.g. `UPDATE ... WHERE state='tripped' AND probe_after <= now`;
- a `probe_in_flight_until`/lease or equivalent;
- cache invalidation on all local state changes, including manual restore and drill activation;
- behavior when the database is locked or unavailable.

A cached breaker state is reasonable for the hot path only if probe claims and trips are authoritative atomic writes, not cache-mediated decisions.

### [MAJOR] The proposed fallback chain does not enforce capability eligibility or the architecture’s intended per-task chains

**File:** `AI_AUTO_FAILOVER_P2_DESIGN.md`, §3 and §8  
**Related file:** `AI_SWAP_ARCHITECTURE.md`, §3 and §4  
**Related file:** `ai_provider.py`, `ADAPTERS`, `TASK_MODEL`, `complete()`

P2 describes:

> “Per provider·task, not global — vision can trip while text lanes stay up”

but its routing pseudocode uses:

```python
chain = [active] + [others]  # today's order, unchanged
```

The actual code similarly falls through every member of `ADAPTERS`:

```python
for alt in [p for p in ADAPTERS if p!=prov]:
```

That is not the capability-aware, per-task chain specified in the architecture. `AI_SWAP_ARCHITECTURE.md` §3 requires distinct chains and explicitly identifies vision as the constraint. It also calls for Mistral/hosted-open/Karoo membership depending on task and capability.

The P2 design may deliberately be a reduced three-provider implementation, but then it should explicitly define actual allowed chain membership per task and validate it before routing. A task key being present in `TASK_MODEL` is not a sufficient capability assurance, especially for vision and structured outputs.

The statement:

> “chains still end in the zero-AI fallback where one exists”

also is not implemented in the shown seam. `ai_provider.complete()` returns the final failed AI result; it contains no deterministic fallback dispatch. If those fallbacks remain at individual call sites, the design should say so and identify which call sites provide them. Otherwise this is an unverified assurance.

### [MAJOR] The drill semantics conflict with the proposed persistent breaker behavior

**File:** `AI_AUTO_FAILOVER_P2_DESIGN.md`, §6

The design says:

> “`AI_DRILL_BAN=anthropic` ... makes the seam treat that provider as T3-tripped”

and later:

> “Unset the env (or POST /admin/ai-restore) to end the drill.”

If drill activation writes persistent breaker rows tagged `trip_reason='drill'`, simply unsetting the environment variable does not itself close or remove those rows. The provider will remain tripped until a restore action or scheduled probe changes it. That is inconsistent with “unset ... to end the drill.”

There is also a risk that a drill configured by environment variable at boot causes persistent state changes and production-style loud alerts every time the process restarts while the variable remains set.

Clarify whether drill is:

1. a non-persistent routing overlay evaluated on every call; or
2. a persisted breaker trip with an explicit drill-end operation.

If it is persistent, unsetting an environment variable cannot be claimed to end it. If it is an overlay, it should not mutate genuine health state or trigger normal T3 escalation without intentional drill-specific alert routing.

### [MAJOR] Sensitive error data may be exposed to n8n and the dashboard without a data-handling policy

**File:** `AI_AUTO_FAILOVER_P2_DESIGN.md`, §5

The alert payload includes:

> “provider, task, trip_reason, last_error, timestamp”

and `/flags.ai_provider` exposes:

> “last_error”

Provider error messages can include request identifiers, account/org identifiers, model names, endpoint details, and potentially echoed malformed prompt fragments. The project handles user listings and KYC content; forwarding raw provider responses to n8n or exposing them in a dashboard can create an unnecessary data-exposure path.

The design should require:

- bounded, sanitized error summaries;
- no request body/prompt/image content in logs, breaker rows, or webhook payloads;
- restricted access to the breaker diagnostics;
- an audit event for manual restore;
- confirmation that the “admin-token” endpoint has the same authentication, authorization, rate limiting, and CSRF protections as other state-changing admin endpoints.

“Admin-token” alone is not enough detail to assess exposure.

### [MINOR] Trip-rule semantics need tightening around 429s, client errors, and “consecutive” failures

**File:** `AI_AUTO_FAILOVER_P2_DESIGN.md`, §2

T1 is:

> “3 consecutive adapter failures (exception/timeout/5xx) within 120 s”

T2 is:

> “≥ 20 % not-ok”

Questions left unresolved by the stated rules:

- Does a 429 count only toward T2, or does it also count as a T1 adapter failure?
- Do 400/422 invalid-request/schema failures count as T2 “not-ok”? If so, a deployment bug or unsupported request format can trip every lane and obscure the actual bug.
- Does a successful fallback result count as success for the failed provider? It must not.
- Does a successful request reset the T1 consecutive counter immediately?
- Is `window_start` reset after a trip, after expiry, or after any success?
- Are timeouts measured at adapter timeout, upstream latency, or caller cancellation?
- Is the “p95 latency > 3× baseline” T2 condition in the architecture intentionally omitted from P2, or deferred?

The last point is a document discrepancy: `AI_SWAP_ARCHITECTURE.md` §2 lists latency degradation as part of T2, while P2 implements only error rate.

## The three findings the System Engineer should discuss first

1. **T2 is impossible with the proposed data model.** The schema has no rolling request denominator or outcome history, so the stated “10 calls and 20% failures in 10 minutes” rule cannot be computed correctly.

2. **The half-open success path violates manual fail-back.** Automatically closing a breaker re-enables the original first-choice provider and therefore automatically returns traffic to it. Health recovery and routing restoration must be separate states/actions.

3. **Heartbeat probes cannot use ordinary `complete()` semantics.** Current fallback behavior means a failed target probe can return a successful alternate-provider result. Probes need direct target invocation, fallback suppression, and atomic single-probe claiming.
